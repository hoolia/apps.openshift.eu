# mailu 0.2.5

Released 2026-11-13.

## Changes

### Mail volume ReadWriteMany, pods on any node

The mail volume is ReadWriteMany (`upstream.persistence.accessModes`). The pods of admin,
dovecot, postfix, rspamd and webmail no longer carry a podAffinity that keeps them on one
node.

Before, they shared a ReadWriteOnce volume. When one of them was evicted and scheduled on
another node, the volume could not attach there and that pod stayed in `ContainerCreating`.

The StorageClass must support ReadWriteMany, CephFS or NFS for example.

## Upgrade

A volume claim cannot change its access mode, so Argo CD and `helm upgrade` fail on an
existing claim `mailu-storage` until it is ReadWriteMany. Migrate the claim first, without
copying data: the access mode of the volume itself can change.

1. Keep the volume when its claim goes:

   ```bash
   PV=$(oc -n <namespace> get pvc mailu-storage -o jsonpath='{.spec.volumeName}')
   oc patch pv "$PV" -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'
   ```

2. Stop automatic sync of the Application, then scale the Mailu Deployments to 0.
3. Save the claim and delete it:

   ```bash
   oc -n <namespace> get pvc mailu-storage -o yaml > mailu-storage.yaml
   oc -n <namespace> delete pvc mailu-storage
   ```

4. Make the volume ReadWriteMany and free it for a new claim:

   ```bash
   oc patch pv "$PV" --type=json -p '[
     {"op":"replace","path":"/spec/accessModes","value":["ReadWriteMany"]},
     {"op":"remove","path":"/spec/claimRef"}]'
   ```

5. Create the claim again from `mailu-storage.yaml`, with `accessModes: [ReadWriteMany]`,
   `volumeName: <PV>`, and without `status`, `uid`, `resourceVersion` and
   `creationTimestamp`. Wait for `Bound`.
6. Upgrade the Application to this version and switch automatic sync on again. Set the
   reclaim policy of the volume back to the one of its StorageClass.
