# chatwoot 0.2.0

## Changes

### Agent Bot through an A2A agent

With `agentBot.enabled` customers in the inboxes of `agentBot.inboxes` get their answers
from an A2A agent (`agent.url`) until they ask for a person, the agent answers with the
handoff marker, or the agent fails; the conversation then goes to staff. The prepare Job
creates the bot, its access token and its webhook secret, and connects it to the listed
inboxes on every install and upgrade. A bridge Deployment checks the signature of every
webhook and keeps one A2A context per conversation in the conversation's custom
attribute `a2a_context_id`.

### Agent panel in the conversation sidebar

With `copilotPanel.enabled` (needs `sso.enabled`) the Job registers a Dashboard App: a
panel next to every conversation where staff ask the same agent to summarise the
conversation, suggest a reply (put into the reply box, never sent) or answer a question.
The panel runs in the oauth2-proxy pod behind the staff login.

### Bridge next to the agent

With `agentBridge.standalone.enabled` a release of this chart runs the bridge alone, with a
Route, in the agent's cluster; the Chatwoot release names it in `agentBridge.remoteUrl`.
Webhooks stay signed, panel requests carry the staff member's own access token (checked
against `agentBridge.standalone.staff`), and the bridge posts the bot's answers to the
public Chatwoot address with the bot's access token.

### Agent credentials

`agent.auth.type` is `none`, `serviceAccountToken` (a token of ServiceAccount
`chatwoot-agent-bridge` for `agent.auth.audience`) or `clientAssertion` (that token as the
client assertion of an OAuth client credentials grant). No credential of the agent is
stored.

## Upgrade

Nothing to do: both features are off by default. Chatwoot refuses webhooks to private
addresses; with `agentBot.enabled` web and worker allow the bridge Service alone.
